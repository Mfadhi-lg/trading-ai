## Implemented contract

- `check_schema_compatibility(conn)` reads the ledger without creating tables,
  taking filesystem locks or applying SQL. Missing schema, pending migrations
  and unexplained applied identities fail with an explicit error.
- `init_db(conn)` retains its import path as a compatibility facade and checks
  by default, including for arbitrary custom DB paths. Migration requires
  `apply_migrations=True`; `apply_migrations(conn)` is the separate writer.
  The existing `init-db --db PATH` command opts in deliberately, retaining its
  name, arguments, success JSON and exit code.
- `connect(..., read_only=True)` requires an existing database and uses SQLite
  `mode=ro` plus `query_only=ON`. It does not create store directories or change
  journal mode. Fourteen view/monitor/export/report CLI branches use it;
  the printed Trendlyne plan uses it unless persistence was explicitly selected.
- The exact historical `065_exchange_source_access.sql` identity is recognized
  separately from canonical browser 065. Other absent-source ledger identities
  fail. No historical SQL filename or bytes were changed.
- Disposable tests now prepare absent fixture databases explicitly before
  workflows. Existing writer connections and workflow business logic remain
  otherwise unchanged. Dry-run tests retain their no-bootstrap behavior.

Deliberate behavior change: routine worker/report/UI initialization and fresh
workflow calls no longer bootstrap schemas or apply newly visible migrations.
Uninitialized databases require the explicit migration action. Writable target
identity enforcement remains H03/C05 work; this chunk does not claim that an
explicit migration command is safe against a mistakenly selected live target.
