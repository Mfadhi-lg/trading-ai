## 3. Apparent duplicates and unique behavior

- Scheduling overlap is real: old company/cap loops duplicate responsibilities now admitted by the installed dispatcher. Full exchange scheduling is **not equivalent**: it also processes registry security/corporate datasets, retry rungs, revision sweeps, missed-day catch-up and weekly reports. Retain that maintenance path; do not activate its standing scheduler alongside the approved clock.
- `artifact-reconciler` overlaps new expectation discovery, but performs all-history startup backfill and broader reconciliation. Phase 4 historical_limit=0 cannot replace it. Periodic dispatch is still an opt-in candidate with durable housekeeping cursors, recovery rotation and changed expectation grouping. Its own runbook acknowledges potentially more company requests. It is not a verified automatic replacement.
- `pipeline/run_document_download_worker.py` delegates to `workflows/documents/download.py`; these are not two independent download executors. The facade passes its module via dynamic `__import__` as `_hooks`, preserving patched claim/persist/reconciliation bindings. Its ownership tests explicitly depend on that contract.
- `documents/downloader.py` delegates ordinary transfer to `documents/download/transport.py` and retains specialized recording streaming/temporary cleanup. Deleting either loses behavior. `fetch_documents.py` is a symbol-selected D02 direct operation with its own evidence/report contract, while the canonical generic worker uses durable scope membership, leases and exact job fencing. Convert only with explicit persistence/output compatibility proof; no such conversion is authorized here.
- Direct-rating, generic alternate-source recovery and browser recovery have distinct queues, resolver/HTML derivative and operator-authorization contracts. Three direct-rating services use one `RatingWorker` implementation with separate host configurations, not three duplicated algorithms. New routine rating consumption does not cover historical/browser recovery runs.
- Quarter direct extraction, scope extraction, frozen campaigns, browser follow/derivative repair and routine inbox extraction all converge on `pipeline.extract_document.extract_document`. Their selectors, persistence and residual normalization stages differ. Retain historical selectors/campaign manifests and parser/OCR version identity; remove only the verified old shell owner.
- `pipeline/scheduler.py`, `screener_vertical.py`, `exchange_universe.py` and other old pipeline names largely forward to canonical workflow owners. CLI dispatch loads handlers from strings, and `cli.__getattr__` loads constant owners dynamically. Low static reference counts cannot establish unreachability.

## 4. Simplification estimate

Minimal patch: **17 → 15 root Compose services; 11 → 9 unprofiled service definitions**, four service blocks removed across production/development, plus obsolete launcher startup removed. It removes 70 old lines and adds only the needed refusal/message updates. The stopped June shell container can be retired separately. No new worker, queue, wrapper or administrative framework is added.

There is **no measured immediate CPU/RAM saving**: the replaced containers are already stopped. The practical gain is eliminating two maintained loop implementations and three stale resumable owners, reducing accidental broad startup and conflicting scheduling. Normal automatic work already uses one minute admission clock, transient bounded containers and one production writer-owner lock. The remaining unprofiled maintenance definitions mean broad `docker compose up` remains inappropriate. A later change to opt-in maintenance profiles requires checking exact service-name callers and browser `extends` behavior; it is not silently included here.

Collection coordinator's priority gate and periodic housekeeping/recovery remain UNKNOWN as retirement candidates: tests/CLI/runbooks demonstrate unique capabilities, but no active production schedule selects them. Capacity-agent removal also remains UNKNOWN because manual document roles still require the fresh-capacity file. Decommissioning a failing agent is not equivalent to deleting its capacity-publisher command.

This cleanup improves operational clarity and startup safety; it does not establish higher corpus throughput or authorize concurrency/rate increases.

The audit identifies actual removable loop code, while distinguishing retained maintenance implementations and investigated unknowns. Runtime deletion and the unified wake/shutdown migration remain post-trial work with the gates above.
