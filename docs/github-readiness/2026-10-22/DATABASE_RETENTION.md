## Required retention before any cleanup

Reuse AR-01.3A's independent snapshot/restore evidence for that exact dated input; reuse B/C's schema/data/control comparison for their exact inputs. Prior evidence retains historical FK defects (10,771 identities in the parent acceptance scope); it is not a whole-database clean-FK claim. Never restore old068/075 snapshots over later accepted business data.

For a future current backup, explicitly schedule quiescence with the current lifecycle and retain pause; verify no owners, active leases or ambiguous WAL/kernel locks. Use a consistent SQLite backup/export to a **different physical device**, independently verify schema/ledger/integrity, counts and hash, and restore into isolated storage. Preserve `/data/snapshots` and required exports as well as DB bytes. Copy the external immutable-document tree with a matching DB/content manifest; verify every referenced original hash and derivative relationship before claiming a restorable corpus. Keep encrypted restricted configuration/credentials separately and add offsite protection. No destination, backup operation, data move or credential change is approved or performed by this audit.

Select durable retention for OCI packages, C03/C26 archives and `/private/tmp` release configurations; record exact file hashes, ownership, modes, source/DB/content snapshot identity and a tested recovery path. A local second filename or a copy on the same external drive is not independent disaster recovery. Only after these gates can specific duplicate copies become cleanup candidates.
