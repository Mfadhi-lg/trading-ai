## 8. Classification and root cause

**Primary classification: flaw in the canary procedure itself.** The procedure assumes `mode=ro` can read this WAL-mode DB through a fully read-only mount even when the WAL/SHM sidecars are absent. SQLite may need to initialize adjacent WAL/shared-memory state when accessing database pages; `mode=ro` and query-only protect SQL/database writes but do not make a WAL-mode connection immutable. The volume mount prevents that initialization. The matching failure and successful guarded immutable diagnostic strongly support this mechanism; no syscall trace was captured, so the exact attempted sidecar operation is an inference rather than an observed syscall.

- **Application code:** not executed by the failing script. Its `connect(read_only=True)` constructs the same `mode=ro` URI, so it shares the procedure's unhandled filesystem condition. No general application regression is established.
- **Configuration:** the intentional read-only mount plus connection mode expose the incompatibility; no wrong DB path or required environment value was found.
- **Missing dependency:** no; Python and SQLite executed and the diagnostic read succeeded.
- **Missing file/mount:** no; the intended DB exists and was readable. Absent sidecars are the relevant WAL state, not an absent main DB or volume.
- **Permissions:** the mount disallows writes needed for sidecar setup; the main DB's ownership/mode permits reading. No evidence supports changing ownership or making production writable as the fix.
- **Health-check logic:** not the source of the returned traceback. The command did inherit the image health-check definition because it did not pass `--no-healthcheck`; its execution was not captured. The embedded image health check uses ordinary `sqlite3.connect(DB_PATH)`, while candidate Compose overrides it with `mode=ro`. This is an additional isolation weakness for a one-shot read-only harness, not evidence that health caused the observed exception.
- **Capacity-state dependency:** no; no capacity function or document path is used.
- **Operator-policy dependency:** no; no runtime write authorization or recovery operation is called. The concrete failure is a SQLite filesystem exception, not an authorization rejection.

There is a separate expected gate after the opener is corrected: the complete C28.1 compatibility check will reject current production schema 068 because 069–075 remain pending. Under this narrowed instruction, that is an honest compatibility result, not permission to migrate or bypass the check. Fixing the opener cannot prove a completed 075 activation.

## 9–10. Correctability and smallest proposed fix — not applied

**Yes: correct the canary harness/procedure without changing production data or the release image.** Propose a guarded immutable read for an independently established quiescent DB with **no WAL present**, then query-only and the existing schema checks. Scope `immutable=1` to this one-shot harness; do not add it globally to application connections. Refuse the immutable path if a WAL exists or DB stability/ownership cannot be established. A presence check alone is insufficient if a writer could create WAL during the probe. Any WAL-present alternative must use a separately verified consistent disposable snapshot or another reviewed WAL-safe approach, not ignore WAL or grant write access to production.

For the same one-shot harness, explicitly disable the inherited image health check with `--no-healthcheck`, so only the declared Python probe runs. Keep the pinned image, network disabled and production volume read-only. Report schema 068/pending identities as a failed current-release compatibility gate, without applying migrations.

This is a proposed procedural change requiring review against the earlier instruction to call application `connect(read_only=True)`. No opener, script, runbook, image, command or production state was changed in this diagnosis. The smallest next action is **prepare the harness-only correction for review**, without executing it.
