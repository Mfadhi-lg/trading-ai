## Migration mechanics and shared acceptance rules

The exact pinned runner is `scrapper.db.database.apply_migrations`: full-filename lexical order, `.migrate.lock` flock plus in-process lock, SQL through `executescript`, then a ledger INSERT. **There is no BEGIN/COMMIT transaction covering a whole file or the seven-file sequence.** Individual SQLite statements have their own atomicity, but earlier successful DDL can persist before a later statement or ledger INSERT fails. A power/interruption failure therefore requires actual-state reconciliation, not assumptions from the ledger alone. The demonstrated 069 failure is direct evidence.

All files are additive. There are **no UPDATE, DELETE, DROP, table rebuilds, data-copy INSERTs or historical seeds**. Migration 072 creates a trigger that affects future `artifact_contents` INSERTs only; it does not fire on existing content. New indexes operate on newly created empty tables. Nullable unconstrained TEXT ADD COLUMN in 069 does not require a rewrite/validation scan of the three existing queues. Large-table scans belong to validation/fingerprinting/integrity/FK checks, not these SQL operations.

The replay rule is the same for every file: **not idempotent if ledger is absent and any DDL has already persisted**. ADD COLUMN and CREATE statements lack IF NOT EXISTS. Only a fully recorded/verified successful migration is safely skipped by the runner; AR-01.1 proves a second completed apply is inert. Never add/fabricate ledger rows, skip a partial file or remove columns/tables to force retry.

Lock estimates below are **planning estimates**, not measurements or guarantees. AR-01.1 logs application and the first post-application fingerprint in the same `10:49:29Z` second, supporting fast aggregate metadata work; per-file lock duration was not instrumented. On quiescent healthy local storage expect milliseconds to a few seconds per file; budget **1–5 seconds each, 60 seconds aggregate diagnostic threshold**. Filesystem stalls, fsync, schema parsing or lock contention can exceed this. Connection busy timeout is 5 seconds. If unexpectedly slow/locked, freeze widening and collect diagnostics; do not automatically force-kill a DDL process without the recovery operator's reconciled decision. Full integrity/row scans took minutes and are outside the 15-minute canary observation window.

Retained clone size rose from **14,602,158,080 to 14,602,240,000 bytes: 81,920 bytes (80 KiB)** after all migrations ([observation](../baselines/AR-01.3/migration-activation-review/clone-size-observation.json)). Per-file growth was not measured. Estimates below describe small page allocations/metadata only, with a conservative **1 MiB main-file growth alert** for review, not a promised maximum. WAL/SHM, freelist reuse, schema overflow and fsync vary; reserve at least **1 GiB additional DB-volume headroom**, and stop on unexplained large growth rather than accepting a percentage of the 14.6 GB corpus.
