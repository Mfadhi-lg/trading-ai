2. **Existing `reconcile_processing` for one selected content — NOT FIRST.** DB-only and explicit IDs, normally two INSERTs plus an optional cached-result UPDATE. ## Restart/idempotency and safe recovery

The underlying `claim_extraction` function **is not replay-idempotent**: it upserts RELEASED or expired rows and rotates fencing tokens. The absent-key check, fixed PK, stopped writers and host single-attempt lock are essential. Never re-run it merely because a receipt is missing. A repeated normal invocation finds the key and stops **before writes**. A matching RELEASED row is verified as already completed, with zero further writes; do not reclaim it. A fresh experimental run requires a newly reviewed key/selection, not incrementing run IDs automatically.

- **Before claim commit:** row absent; preserve error/logs, then the user may authorize a new attempt after a fresh absent-key gate. No routine retries.
- **Claim committed; release not committed:** only the isolated ACTIVE row can remain. No real job was claimed. Preserve token/owner/expiry and command timeline. Existing `release_extraction(conn,captured_claim)` can perform a **single conditional forward UPDATE** for exact PK+owner+token+ACTIVE state, under explicit user authorization; it can release after lease expiry without taking ownership of another generation. Require rowcount1, unchanged other fields and no real work references. If token differs or ownership is ambiguous, stop; never use unconditional clearing/upsert/delete.
- **Release committed; receipt lost:** matching RELEASED row is terminal metadata, not evidence that extraction occurred. Complete read-only verification and receipt reconstruction; no DML.
- **Any extra row/queue/file/source effect:** stop and preserve DB/sidecars and exact diff. No broad requeue, old-image restart or pre075 database restore. Do not overwrite later legitimate writes with the 068 or075 snapshot.

If the process dies after commit but before logging the generated token, a read-only snapshot of that exact key provides the candidate token/owner. Recovery still needs user review tying it to the reserved PK, prepared run timestamp/60-second expiry and sole-owner window; absent trustworthy linkage is a STOP, not permission to seize the current row. No credentials or operator powers are invented. User remains recovery authority; Codex executes only selected scope. Prefer leaving/verifying the released receipt over deleting it. No whole-DB rollback is needed for this isolated row; the narrowly fenced forward path is ready without solving generalized business-write recovery.
